1. Objetivo de esta guía

Esta guía establece una forma estándar para crear, organizar y completar historias de usuario dentro de GitHub Projects.

El objetivo es que todos los integrantes del equipo entiendan:

  • Qué debe contener una User Story.
  • Cuándo crear una User Story, Task, Bug o Epic.
  • Cómo escribir criterios de aceptación.
  • Cómo utilizar los campos del tablero.
  • Cuándo una tarjeta puede considerarse completada.
  • Cómo evitar historias demasiado grandes, ambiguas o técnicas.
Regla principal: Toda User Story debe cumplir con Contexto + Criterios de Aceptación.

2. Estructura de una User Story

Una User Story debe describir una necesidad desde la perspectiva de quien utilizará el sistema.

La estructura obligatoria es:

Como [tipo de usuario / rol]

Quiero [hacer una acción o tener una funcionalidad]

Para [obtener este beneficio o valor]

Ejemplo correcto

Como cliente

Quiero iniciar sesión utilizando mi correo y contraseña

Para acceder de forma segura a las funcionalidades de mi cuenta

Ejemplo incorrecto

Crear endpoint POST /login.

Esto describe una tarea técnica y no una necesidad del usuario. Puede convertirse en una Task asociada a una User Story.

3. El contexto de la User Story

La frase "Como / Quiero / Para" explica qué se necesita y por qué, pero el equipo puede necesitar información adicional para entender correctamente el problema.

Por eso, una buena User Story puede incluir una sección de Contexto.

Ejemplo

Como: cliente

Quiero: iniciar sesión utilizando mi correo y contraseña

Para: acceder de forma segura a las funcionalidades de mi cuenta

Contexto

Actualmente el sistema no permite autenticar usuarios. El usuario debe poder ingresar sus credenciales desde el formulario de inicio de sesión para acceder a las funcionalidades correspondientes a su rol.

Importante: El contexto explica el problema o situación. No debe convertirse en una explicación técnica de cómo implementar la solución.

4. Criterios de aceptación

Los criterios de aceptación son las condiciones que deben cumplirse para considerar terminada una User Story.

Funcionan como una lista de pruebas que el equipo puede utilizar para verificar que la funcionalidad cumple con lo solicitado.

Regla de oro: Una User Story sin criterios de aceptación no está completa y debe ser rechazada antes de pasar al desarrollo.

Características de buenos criterios

  • Deben ser claros.
  • Deben poder comprobarse.
  • No deben depender de interpretaciones.
  • Deben describir el comportamiento esperado.
  • Deben indicar qué ocurre en casos normales y relevantes.
  • Deben incluir errores importantes cuando corresponda.

Ejemplo

User Story:

Como cliente quiero iniciar sesión utilizando mi correo y contraseña para acceder de forma segura a mi cuenta.

Criterios de aceptación:

  • El formulario debe solicitar correo y contraseña.
  • El sistema debe validar que ambos campos hayan sido ingresados.
  • Las credenciales correctas deben permitir el acceso al sistema.
  • Las credenciales incorrectas deben mostrar un mensaje de error.
  • El usuario debe ser redirigido a la página correspondiente después de iniciar sesión.
  • La contraseña no debe mostrarse como texto visible.

5. Formato recomendado: Given / When / Then

Cuando una historia tenga comportamientos complejos, los criterios pueden escribirse utilizando el formato Given / When / Then.

Elemento Significado
Given Situación inicial.
When Acción realizada por el usuario.
Then Resultado esperado. 

Given que el usuario tiene una cuenta registrada
When introduce un correo y contraseña válidos
Then el sistema debe permitirle acceder a su cuenta

Este formato es especialmente útil para funcionalidades que posteriormente serán probadas de forma manual o automatizada.

6. Uso de los campos en GitHub Projects

Los campos del proyecto deben utilizarse de manera consistente. Esto permite filtrar, ordenar y visualizar el trabajo del equipo.

Category

Categoría Uso Ejemplo
Epic Módulo o funcionalidad grande que agrupa varias User Stories. Sistema de Autenticación
User Story Funcionalidad que aporta valor directo al usuario. Iniciar sesión
Task Trabajo técnico necesario para implementar una funcionalidad. Crear endpoint POST /login
Bug Error inesperado del sistema que debe corregirse. El botón de login no responde
Regla práctica: Si el elemento describe algo que el usuario necesita, probablemente sea una User Story. Si describe algo que el desarrollador necesita hacer para construirla, probablemente sea una Task.

7. Campo Area

El campo Area indica qué parte del proyecto está principalmente involucrada.

Area Ejemplos
Frontend Angular, interfaces, componentes, formularios.
Backend API, lógica de negocio, endpoints.
Database PostgreSQL, tablas, relaciones, consultas.
Infrastructure Docker, CI/CD, servidores, despliegues.
Documentation Manuals, documentación técnica, diagramas.

Si una User Story requiere varias áreas, se recomienda asignar el área principal a la historia y utilizar Tasks específicas para cada área involucrada.

8. Campo Priority

Prioridad Significado Ejemplos
P1 - Alta Trabajo crítico o que bloquea otras partes del proyecto. Docker, CI/CD, autenticación necesaria para continuar.
P2 - Media Funcionalidad importante que forma parte del objetivo del Sprint. CRUD principal, búsqueda, reportes.
P3 - Baja Mejoras que pueden esperar sin afectar el objetivo principal. Mejoras visuales, refactorización, pequeños ajustes.
P1 no significa "quiero terminarlo primero". Debe utilizarse cuando el trabajo tenga un impacto crítico, sea un bloqueo o sea necesario para que otras funcionalidades puedan avanzar.

9. Cómo nombrar las tarjetas

El título debe ser corto y permitir identificar rápidamente qué se está trabajando.

Recomendado

  • Iniciar sesión
  • Registrar usuario
  • Consultar productos
  • Crear pedido
  • Editar perfil

Evitar

  • Hacer login
  • Implementar todo el backend del usuario
  • Arreglar varias cosas
  • CRUD usuarios completo

El título identifica la tarjeta. La descripción contiene la información necesaria para comprender y validar el trabajo.

10. Tamaño de una User Story

Una User Story debe ser suficientemente pequeña para poder completarse dentro de un Sprint.

Señal de alerta: Si una historia contiene demasiadas funcionalidades, probablemente debe dividirse.

Ejemplo demasiado grande

Gestionar usuarios

Registrar usuarios, iniciar sesión, editar perfiles, cambiar contraseñas, eliminar usuarios, asignar roles, recuperar contraseñas y consultar usuarios.

Mejor división

  1. Registrar usuario.
  2. Iniciar sesión.
  3. Editar perfil.
  4. Cambiar contraseña.
  5. Recuperar contraseña.
  6. Consultar usuarios.
  7. Asignar roles.
  8. Eliminar usuario.

11. Cómo dividir una User Story en Tasks

Las Tasks representan el trabajo necesario para implementar una User Story.

Ejemplo

User Story: Iniciar sesión

Como cliente quiero iniciar sesión utilizando mi correo y contraseña para acceder de forma segura a mi cuenta.

Tasks

  • Crear formulario de login en Angular.
  • Crear endpoint de autenticación en Go.
  • Implementar validación de credenciales.
  • Implementar generación del token.
  • Conectar el frontend con el endpoint.
  • Mostrar mensajes de error.
  • Realizar pruebas.
Las Tasks pueden ser técnicas. La User Story no debería convertirse en una lista de Tasks.

12. Cómo reportar un Bug

Un Bug representa un comportamiento que no funciona como debería.

Estructura recomendada

  • Descripción: qué está ocurriendo.
  • Pasos para reproducir: cómo provocar el error.
  • Resultado actual: qué sucede.
  • Resultado esperado: qué debería suceder.
  • Impacto: qué tan grave es el problema.

Ejemplo

Bug: El formulario permite iniciar sesión con campos vacíos.

Pasos:

  1. Abrir la página de inicio de sesión.
  2. Dejar correo y contraseña vacíos.
  3. Presionar "Iniciar sesión".

Resultado actual: El sistema intenta realizar la autenticación.

Resultado esperado: El sistema debe solicitar que los campos sean completados.

13. Definition of Done (DoD)

Los criterios de aceptación indican cuándo una funcionalidad cumple con los requisitos. La Definition of Done indica cuándo el trabajo está realmente terminado desde el punto de vista del equipo.

Una tarjeta no debería pasar a Completado solamente porque "el código funciona en la computadora del desarrollador".

Checklist recomendado

  • ☐ Todos los criterios de aceptación se cumplen.
  • ☐ El código fue revisado por otro integrante.
  • ☐ Se realizaron las pruebas correspondientes.
  • ☐ No existen errores conocidos que impidan utilizar la funcionalidad.
  • ☐ Los cambios fueron integrados correctamente mediante Git.
  • ☐ La documentación necesaria fue actualizada.
  • ☐ La funcionalidad puede ejecutarse en el entorno correspondiente.
  • ☐ La Pull Request fue revisada y aprobada.
Definition of Done: Una tarjeta se mueve a "Completado" solamente cuando cumple los criterios de aceptación y la Definition of Done del equipo.

14. Flujo de trabajo recomendado

Para mantener el tablero organizado, se recomienda utilizar un flujo similar al siguiente:

  1. Idea / Backlog: Se identifica una necesidad.
  2. Refinamiento: El equipo analiza la historia y aclara dudas.
  3. Ready: La historia tiene contexto, criterios de aceptación, prioridad y área.
  4. In Progress: Un integrante comienza el desarrollo.
  5. Review: Se realiza Pull Request y revisión de código.
  6. Testing: Se verifican los criterios de aceptación.
  7. Done: Cumple los criterios de aceptación y Definition of Done.

15. Definition of Ready

Antes de comenzar una User Story, el equipo debe comprobar que está suficientemente preparada.

Checklist

  • ☐ Tiene un título claro.
  • ☐ Tiene estructura Como / Quiero / Para.
  • ☐ Tiene contexto cuando sea necesario.
  • ☐ Tiene criterios de aceptación.
  • ☐ Se entiende qué resultado espera el usuario.
  • ☐ Tiene Category.
  • ☐ Tiene Area.
  • ☐ Tiene Priority.
  • ☐ Es suficientemente pequeña para el Sprint.
  • ☐ No existen dudas importantes sin resolver.
Si una historia no está lista para ser desarrollada, no debería entrar al Sprint solamente para "tener algo que hacer".

16. Responsabilidades del equipo

Rol Responsabilidad
Scrum Master Facilitar el proceso, ayudar a mantener el tablero organizado y asegurar que se respeten las reglas acordadas.
Equipo de desarrollo Analizar la historia, identificar Tasks, estimar el trabajo, desarrollar, probar y revisar.
Product Owner Priorizar necesidades y aclarar el valor esperado para el usuario.
El Scrum Master no debería convertirse en la única persona responsable de escribir y mantener todas las historias. El equipo debe participar en el refinamiento.

17. Ejemplo completo para GitHub Projects

US-001: Iniciar sesión

Category: User Story

Area: Backend / Frontend

Priority: P1 - Alta

Como: usuario registrado

Quiero: iniciar sesión utilizando mi correo y contraseña

Para: acceder de forma segura a las funcionalidades de mi cuenta

Contexto

El sistema necesita permitir que los usuarios registrados puedan autenticarse antes de acceder a las funcionalidades protegidas de la aplicación.

Criterios de aceptación

  • El formulario debe solicitar correo y contraseña.
  • Ambos campos deben ser obligatorios.
  • Las credenciales válidas deben permitir el acceso.
  • Las credenciales inválidas deben mostrar un mensaje de error.
  • La contraseña debe ocultarse visualmente.
  • Después de autenticarse, el usuario debe acceder a su página principal.

Tasks

  • Crear formulario de login.
  • Crear endpoint de autenticación.
  • Implementar validación.
  • Implementar generación de token.
  • Conectar frontend y backend.
  • Agregar pruebas.

18. Reglas rápidas del equipo

  1. Sin criterios de aceptación, no hay User Story válida.
  2. Una User Story debe expresar valor.
  3. Las Tasks pueden ser técnicas.
  4. No mezclar múltiples funcionalidades grandes en una sola historia.
  5. Todo trabajo debe tener una tarjeta.
  6. No mover una tarjeta a Done solamente porque terminó la programación.
  7. La Pull Request debe estar relacionada con la tarjeta correspondiente.
  8. El tablero debe representar el estado real del trabajo.
  9. Las historias deben refinarse antes del Sprint cuando sea posible.
  10. Si una historia no se entiende, se pregunta antes de comenzar a programar.
