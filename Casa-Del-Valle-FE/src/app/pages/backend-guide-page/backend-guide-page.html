Guía de desarrollo · Go + PostgreSQL

Backend limpio y reutilizable

Guía interna para trabajar con la estructura Controller → Service → Repository → pgxPool → PostgreSQL. El objetivo es que cualquier integrante pueda crear una nueva entidad siguiendo el mismo patrón sin duplicar conexiones ni mezclar responsabilidades.

Go 1.25 pgx v5 PostgreSQL Docker

1. Arquitectura del backend

La aplicación está organizada por responsabilidades. Una petición HTTP atraviesa las capas en este orden:

HTTP→ Controller→ Service→ Repository→ pgxPool→ PostgreSQL
Controller
Recibe HTTP, valida lo básico, llama al servicio y construye la respuesta JSON.
Service
Contiene las reglas de negocio y coordina operaciones.
Repository
Es responsable de SQL y acceso a datos.
pgxPool
Administra y reutiliza conexiones hacia PostgreSQL.
Idea clave: el pool se crea una sola vez al iniciar la aplicación y se comparte con todos los repositories. No se crea un pool por entidad ni por endpoint.

¿Por qué una carpeta por entidad? Porque evita terminar con carpetas globales gigantes como controllers/, services/ y repositories/ que contienen decenas de archivos. Todo lo relacionado con una entidad queda junto.

¿Qué significa internal/?

En Go, internal es una convención con una regla especial del lenguaje: los paquetes dentro de un directorio internal no pueden ser importados desde código externo al árbol de su módulo. Para nuestro proyecto esto ayuda a mantener la lógica interna del backend encapsulada.

4. Crear y reutilizar el pgxPool

El pool administra un conjunto de conexiones reutilizables. La aplicación debe tener un único pool compartido.

internal/database/postgres.go

package database

import (
    "context"
    "fmt"
    "os"
    "time"

    "github.com/jackc/pgx/v5/pgxpool"
)

func NewPostgresPool(ctx context.Context) (*pgxpool.Pool, error) {
    host := os.Getenv("DB_HOST")
    port := os.Getenv("DB_PORT")
    user := os.Getenv("DB_USER")
    password := os.Getenv("DB_PASSWORD")
    dbname := os.Getenv("DB_NAME")

    dsn := fmt.Sprintf(
        "postgres://%s:%s@%s:%s/%s",
        user,
        password,
        host,
        port,
        dbname,
    )

    config, err := pgxpool.ParseConfig(dsn)
    if err != nil {
        return nil, err
    }

    config.MaxConns = 10
    config.MinConns = 2
    config.MaxConnLifetime = time.Hour

    pool, err := pgxpool.NewWithConfig(ctx, config)
    if err != nil {
        return nil, err
    }

    if err := pool.Ping(ctx); err != nil {
        pool.Close()
        return nil, err
    }

    return pool, nil
}

¿Qué está pasando?

  • context.Context acompaña la operación y permite manejar cancelación y límites de tiempo.
  • os.Getenv() obtiene las variables de entorno.
  • El DSN describe cómo conectarse a PostgreSQL.
  • pgxpool.ParseConfig() convierte el DSN en configuración.
  • pgxpool.NewWithConfig() crea el pool.
  • Ping() verifica que realmente podamos comunicarnos con PostgreSQL.
  • La función devuelve (*pgxpool.Pool, error): resultado si todo salió bien o error si falló.
No hagan esto: crear pgxpool.New... dentro de cada repository, método o endpoint. El pool es un recurso compartido de toda la aplicación.

5. Crear el pool en main.go

main.go es el punto donde se construye la aplicación y se conectan sus dependencias.

package main

import (
    "context"
    "log"
    "net/http"

    "github.com/joho/godotenv"

    "github.com/tu-organizacion/cdv-api/internal/database"
    "github.com/tu-organizacion/cdv-api/internal/users"
)

func main() {
    if err := godotenv.Load(); err != nil {
        log.Println("No se encontró .env; se usarán variables del entorno")
    }

    ctx := context.Background()

    pool, err := database.NewPostgresPool(ctx)
    if err != nil {
        log.Fatalf("Error conectando a PostgreSQL: %v", err)
    }
    defer pool.Close()

    userRepository := users.NewRepository(pool)
    userService := users.NewService(userRepository)
    userController := users.NewController(userService)

    mux := http.NewServeMux()

    mux.HandleFunc(
        "GET /usuarios",
        userController.GetUsers,
    )

    log.Println("Servidor escuchando en :8080")

    if err := http.ListenAndServe(":8080", mux); err != nil {
        log.Fatal(err)
    }
}
Este patrón se llama inyección de dependencias: main crea las dependencias y se las entrega a las capas que las necesitan. Así los repositories no tienen que saber cómo crear la conexión.

El flujo

main
 │
 ├── crea pool
 │
 ├── Repository(pool)
 │       ↓
 ├── Service(repository)
 │       ↓
 └── Controller(service)
         ↓
       HTTP

6. Crear el modelo de una entidad

Ejemplo para users:

package users

type User struct {
    ID     int64  `json:"id"`
    Nombre string `json:"nombre"`
    Email  string `json:"email"`
}

Un struct agrupa datos relacionados. Los tags json indican cómo se representan los campos al convertirlos a JSON.

7. Repository: acceso a PostgreSQL

El repository es la capa donde vive el SQL. Recibe el pool que creó main.

package users

import (
    "context"

    "github.com/jackc/pgx/v5/pgxpool"
)

type Repository struct {
    pool *pgxpool.Pool
}

func NewRepository(pool *pgxpool.Pool) *Repository {
    return &Repository{
        pool: pool,
    }
}

func (r *Repository) GetAll(ctx context.Context) ([]User, error) {
    rows, err := r.pool.Query(
        ctx,
        `SELECT id, nombre, email
         FROM usuarios
         ORDER BY id`,
    )

    if err != nil {
        return nil, err
    }

    defer rows.Close()

    var usuarios []User

    for rows.Next() {
        var user User

        if err := rows.Scan(
            &user.ID,
            &user.Nombre,
            &user.Email,
        ); err != nil {
            return nil, err
        }

        usuarios = append(usuarios, user)
    }

    if err := rows.Err(); err != nil {
        return nil, err
    }

    return usuarios, nil
}

Reglas para SQL

Nunca concatenen datos del usuario en SQL.

Incorrecto:

query := "SELECT * FROM usuarios WHERE email = '" + email + "'"

Correcto:

query := `
    SELECT id, nombre, email
    FROM usuarios
    WHERE email = $1
`

row := r.pool.QueryRow(ctx, query, email)

Los parámetros $1, $2, etc. deben utilizarse para valores provenientes de peticiones, formularios o cualquier otra entrada externa.

Métodos principales de pgxPool

Método Uso
Query() Cuando esperamos múltiples filas.
QueryRow() Cuando esperamos una sola fila.
Exec() INSERT, UPDATE, DELETE u operaciones sin filas de resultado.
Ping() Comprobar conectividad.

8. Service: reglas de negocio

El service no debería contener SQL. Su responsabilidad es aplicar reglas de negocio y coordinar repositories.

package users

import "context"

type Service struct {
    repository *Repository
}

func NewService(repository *Repository) *Service {
    return &Service{
        repository: repository,
    }
}

func (s *Service) GetUsers(ctx context.Context) ([]User, error) {
    return s.repository.GetAll(ctx)
}

Al principio puede parecer que el service solo "pasa" la llamada al repository. Está bien. Su valor aparece cuando necesitamos reglas como validar estados, comprobar permisos, combinar varias operaciones o coordinar diferentes repositories.

9. Controller: HTTP y JSON

El controller conoce HTTP; no debería contener consultas SQL.

package users

import (
    "encoding/json"
    "net/http"
)

type Controller struct {
    service *Service
}

func NewController(service *Service) *Controller {
    return &Controller{
        service: service,
    }
}

func (c *Controller) GetUsers(
    w http.ResponseWriter,
    r *http.Request,
) {
    usuarios, err := c.service.GetUsers(r.Context())

    if err != nil {
        http.Error(
            w,
            "Error al obtener usuarios",
            http.StatusInternalServerError,
        )
        return
    }

    w.Header().Set(
        "Content-Type",
        "application/json",
    )

    json.NewEncoder(w).Encode(usuarios)
}
Importante: r.Context() permite pasar el contexto de la petición HTTP hasta PostgreSQL:

HTTP → Controller → Service → Repository → pgxPool → PostgreSQL.

Si la petición se cancela, las operaciones que respetan ese contexto pueden detenerse.

10. ¿Cómo crear una nueva entidad?

Cuando llegue una nueva entidad, por ejemplo products, no se modifica el pool. Se reutiliza. 

internal/
├── database/
│   └── postgres.go
│
├── users/
│   ├── model.go
│   ├── repository.go
│   ├── service.go
│   └── controller.go
│
└── products/
    ├── model.go
    ├── repository.go
    ├── service.go
    └── controller.go

En main.go:

productRepository := products.NewRepository(pool)
productService := products.NewService(productRepository)
productController := products.NewController(productService)

Observa que ambos reciben el mismo pool:

                 ┌── users.Repository
                 │
pgxPool ─────────┼── products.Repository
                 │
                 └── orders.Repository

Checklist para una entidad

  • Crear carpeta internal/<entidad>.
  • Crear model.go.
  • Crear repository.go con SQL.
  • Crear service.go con reglas de negocio.
  • Crear controller.go con endpoints HTTP.
  • Crear las dependencias en main.go.
  • Registrar las rutas en el router.
  • Reutilizar el pool existente.

11. Transacciones

Cuando una operación de negocio necesite varias consultas que deben completarse juntas, se utilizará una transacción.

tx, err := pool.Begin(ctx)
if err != nil {
    return err
}

defer tx.Rollback(ctx)

// INSERT / UPDATE / DELETE ...

if err := tx.Commit(ctx); err != nil {
    return err
}

return nil
No hagan Commit() inmediatamente después de cada consulta si todas forman parte de una única operación lógica. Una transacción permite que las operaciones se confirmen juntas o se reviertan.

Para operaciones complejas, la estrategia de transacciones debe definirse junto con la lógica del service y el diseño de repositories, evitando abrir y cerrar conexiones manualmente.

12. Manejo de errores

Go utiliza explícitamente valores error en lugar de depender de excepciones como en Java. 

resultado, err := algunaOperacion()

if err != nil {
    return nil, err
}

Una regla sencilla para el equipo:

si una función devuelve error:
    comprobar el error inmediatamente
    decidir si se devuelve, transforma o maneja
    no ignorarlo sin una razón

El repository puede devolver el error al service; el service puede devolverlo al controller; y el controller decide qué respuesta HTTP corresponde.

13. Reglas del equipo

1. Un solo pool
El pool se crea al iniciar la aplicación y se comparte.
2. SQL en Repository
No colocar consultas SQL en controllers ni services.
3. Negocio en Service
Las reglas de negocio pertenecen al service.
4. HTTP en Controller
El controller maneja request, response, status codes y JSON.
5. Context siempre
Pasar r.Context() hasta las operaciones de base de datos.
6. Parámetros SQL
Usar $1, $2, etc.; nunca concatenar entrada del usuario.
7. Configuración externa
Credenciales mediante variables de entorno, no hardcodeadas.
8. Entidades aisladas
Cada entidad mantiene juntos su model, repository, service y controller.

Antes de hacer un Pull Request

  • ¿La entidad está dentro de internal/?
  • ¿El repository recibe el pool existente?
  • ¿No se creó otro pool?
  • ¿El SQL usa parámetros?
  • ¿Se utiliza context.Context?
  • ¿La lógica de negocio está en service?
  • ¿El controller solamente maneja HTTP/JSON?
  • ¿Las credenciales están fuera del código?
  • ¿Los errores se comprueban?
  • ¿La nueva dependencia fue conectada desde main.go?

├── model.go       → datos
├── repository.go  → SQL + pgxPool
├── service.go     → reglas de negocio
└── controller.go  → HTTP + JSON
Principio fundamental: las capas conocen hacia abajo, no hacia arriba. El controller llama al service; el service llama al repository; el repository usa el pool. El repository no debe saber nada de HTTP y el controller no debe saber cómo funciona PostgreSQL.
